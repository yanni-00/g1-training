# 目标对齐规约

供 `$requirement` 及设计、实现、训练、调参流程共用。目标逐步澄清是正常输入；agent 负责暴露歧义并将用户意图转换成可验收行为，不要求用户预先写出全部技术规格。

## 记录位置与最小契约

复用 `.oma/requirements.md` 的“交付目标与理解确认”“目标覆盖表”“方向验收”“修订记录”，任务卡只引用当前有效版本及本轮范围；不另建一套目标 JSON 或实验账本。

- **交付行为**：谁给什么输入，系统应出现什么可观察行为；覆盖哪些阶段、工况和持续运行需求。
- **控制与交付边界**：论文复现、算法研究或可用功能；是否限定算法、纯策略学习或允许显式参考 / 混合控制；仿真、离线接口和真机的范围分别记录。没有路线歧义时无需逐项询问。
- **质量与接受方式**：用户关心的形态 / 自然度、必须保留的约束、可接受不足及非目标；可测部分登记指标和来源，暂不能可靠量化的部分保留视频 / 人工验收，不以方便计算的代理量冒充目标。
- **当前版本与来源**：保留用户原话或消息日期 / 标识、agent 的行为复述、已确认内容、未决问题、当前轮所依据的版本。建议、工程阈值、硬件实测与用户要求分栏标明，未知不补估计。

## 对齐触发点

### 正式投入前：确认交付含义

先读已有需求、代码 / 数据与用户指令，再用简短行为描述复述交付；只追问会改变路线、验收或授权范围的未决选择，给出推荐及理由。论文的方法与指标提供技术依据，不能代替项目意图。已有明确表达 / 授权即记录来源并继续，不强求用户再次说“确认”，不重做长问卷。

会改变路线的歧义尚未解决时，先做不依赖该选择、已有授权的只读审计或可逆准备；不要启动依赖该选择的正式训练 / 扫描，也不要求停止其他已授权在跑任务。普通实现细节由 agent 决定。

### 首次行为可见时：确认方向

优先使用已有模型 / 产物；确需新试验时，范围须在现有授权内并预先登记。给出能辨认目标动作的片段、实际指令 / 控制方式、已覆盖和未覆盖项，请用户判断“是不是要的方向”。不能只用奖励曲线或软件 smoke 代替行为演示。

只有静态检查、缺视频或本身不能审阅视觉内容时，记为尚无有效方向证据，交由具备能力的审阅者 / 用户评审，不能填写已通过。方向通过只确认目标理解，不代表性能、总体任务或部署验收通过。

等待反馈期间可整理证据、修复与该选择无关的问题及完成已授权的有限运行；不因用户未回复而默认方向正确或扩成重复优化 / sweep。用户已在相同目标与控制版本下明确接受行为时，沿用该记录。

### 中途收到补充 / 纠正时：确认影响范围

| 类型 | 判断依据 | 动作 |
|---|---|---|
| 理解纠正 | 原意已有依据，agent 遗漏、误读或用代理量替代 | 记录原话、错误理解和纠正；审计受影响方案 / 实验，不一律归为用户改需求 |
| 细节补充 | 方向一致，新增形态、工况或质量细节 | 补覆盖项与未来验收，标明对当前轮的影响 |
| 目标变更 | 用户明确改变所需能力、交付或控制边界 | 登记新版本与适用起点，更新受影响设计 / 计划，保留旧目标下结果 |

分类可逐项不同；证据不足且会影响处置时，用一个聚焦问题澄清，不擅自归责。已有明确修订指令足以更新目标；只询问尚未解决的取舍，不再请求同一次授权。

## 修订与历史保护

`LOCKED` 表示该版本是下游依据，不表示用户以后不能补充。通过 `$requirement` 的增量修订路径更新受影响部分，保留修订前相关文字 / 版本、来源、分类、修改原因、适用实验和影响清单；不重新抽论文或重做完整访谈。新意图不改写论文知识。

当前轮登记 / config 与 verdict 的 note 写明需求版本、本轮覆盖项和控制方式；不改变 decision_log 的 CSV 结构。任务卡镜像同一版本，冲突时追溯来源，无法确定则标未知，不能仅靠修改时间择一。

已登记轮次按原冻结门回填，并在结论中标注哪些结果不适用于当前目标；纠正揭示原协议无效时明确标注有效性缺陷，不伪造或删除旧证据。新增门、诊断和重算分别登记，不倒推旧轮成功。正在运行的任务继续、停止或改动须按既有任务授权处理，目标修订本身不派生云端 stop。

## 覆盖与接受

目标覆盖表按“用户行为 → 输入 / 控制方式 → 阶段 / 工况 → 协议 → 实际指标与视觉证据 → 状态”逐项记录。状态区分：未覆盖、待验、未通过、通过、不适用（附依据）。例如只在停止阶段检查脚底滑动，不能推导行走质量已覆盖；连续 GO 命令也不自动等于持续物理行走。

数值门通过而 owner 认为动作不自然时，保留量化结论和未通过的质量项；数值门未全过而 owner 接受某个版本时，登记接受的模型 / 控制 / 视频、适用范围、可接受不足和后续动作，遵守既有 owner-tolerance 规则。方向认可、候选接受、总体收束和真机授权分别记录；不自动覆盖基线、追加优化或打开部署门。

## 场景检查（用于审查流程，不是实跑验证）

| 请求 / 证据 | 应做的决定 |
|---|---|
| “移植某算法，走得自然”，控制输入与是否允许参考臂未知 | 复述交付，聚焦询问影响路线的选择，不由论文补成项目要求 |
| 用户已明确要手柄速度控制 | 引用现有指令，直接落到指令响应覆盖，不重复问要不要手柄 |
| 首次视频后用户说“我要肘尖向后，不是只垂下前臂” | 对照既有意图，记录纠正或补充，更新形态验收；关节误差下降不代替形态 |
| 用户说“之前就说了要持续走路”且旧消息可证 | 记录 agent 理解纠正，补长期工况；不归为用户临时改目标 |
| 用户明确从固定轨迹改为手柄控制 | 新版本；旧轨迹实验保留原门判定，不能用作新能力证据 |
| 数值门过，但用户指出行走时擦地 | 保留量化结果，记录未覆盖 / 未通过的行走质量及补充诊断 |
| 用户接受参考臂视频，之后只授权一次适配 | 保护接受基线，记录新控制分工与有限授权；不默认纯策略学习成功或无限续训 |
